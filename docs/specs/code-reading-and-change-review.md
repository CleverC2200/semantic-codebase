# 分层代码阅读与 AI 变更风险审阅

## Problem Statement

AI 修改代码的速度超过人逐行理解和审阅的速度。当前阅读原型可以查看文件、函数和静态图，但仍存在信息密度失衡：文件页铺开过多函数细节，函数控制图直接暴露通用语句节点，缺少业务能力分层，也无法明确解释一次修改的行为差异、业务重要程度和潜在影响范围。

用户需要能够逐级压缩、展开和核对代码信息，快速回答：系统能做什么、某件事如何完成、关键逻辑在哪里、AI 改变了什么、哪些位置值得优先核查。压缩不能隐藏关键条件、敏感写入、分析缺口或版本差异。

## Solution

以业务能力和源码组织提供两条导航，以能力概览、Application Flow 主线、SourceFile 文件、Definition 函数四类页面承接阅读。系统、业务域、功能复用能力概览页面骨架；业务归属与跨功能协作分开表达。

页面按阅读对象组织，视图按问题组织。函数呈现函数说明、关键逻辑、调用关系；主线呈现从触发到结果的关键阶段，按需展开数据变化、状态与失败路径。源码与 Evidence 放在关联的辅助面板。简单内容使用紧凑文字或少量步骤，不强迫所有函数使用画布。

提供贯穿各层的重要性和潜在影响提示，以及围绕明确版本比较的变更阅读入口。区分对象长期重要性与本次变更风险，优先解释行为前后差异、证据路径和待验证事项。

## User Stories

1. 作为代码阅读者，我希望从系统进入业务域和功能，以便先理解整体能力再阅读实现。
2. 作为代码阅读者，我希望在功能下看到新增、修改、删除等独立主线，以便按具体目标定位代码。
3. 作为项目维护者，我希望业务归属遵循本项目术语，以便避免套用不合适的通用分类。
4. 作为项目维护者，我希望确认或调整能力候选的归属，以便保留可追溯的业务判断。
5. 作为代码阅读者，我希望待归类内容仍可访问，以便不因业务映射缺失而丢失代码。
6. 作为代码阅读者，我希望区分归属与依赖，以便不会把调用权限校验误读为属于权限管理。
7. 作为代码阅读者，我希望共享能力只维护一份身份和说明，以便避免多个主线重复且矛盾的解释。
8. 作为代码阅读者，我希望切换业务导航和源码目录，以便按问题或代码位置进入。
9. 作为代码阅读者，我希望能力概览只显示职责、下属能力和关键规则，以便快速建立范围认识。
10. 作为代码阅读者，我希望文件页显示文件职责和简洁函数目录，以便知道这里有什么以及从哪里开始读。
11. 作为代码阅读者，我希望函数目录每项默认只有名称和一句用途，以便浏览大文件时不被参数表淹没。
12. 作为代码阅读者，我希望按可靠职责分组并能切回源码顺序，以便兼顾理解和定位。
13. 作为代码阅读者，我希望没有分组证据时保留原顺序，以便不被猜测的分类误导。
14. 作为代码阅读者，我希望类型、其他定义和完整源码按需展开，以便保持文件首屏简洁。
15. 作为代码阅读者，我希望直接进入函数正文，以便不必在整个文件里再次寻找它。
16. 作为代码阅读者，我希望函数关键逻辑展示动作、条件和结果，以便理解行为而非阅读重复的“处理语句”。
17. 作为代码阅读者，我希望关键分支、循环、异常和提前返回被保留，以便压缩后仍能正确理解函数。
18. 作为代码阅读者，我希望简单函数不使用空旷大画布，以便减少视觉负担。
19. 作为代码阅读者，我希望看到直接调用者和下游依赖，以便理解函数的协作位置。
20. 作为代码阅读者，我希望查看调用中的参数和结果用途，以便知道接口之间交换什么。
21. 作为代码阅读者，我希望调用关系不暗示执行顺序，以便避免把依赖图当运行轨迹。
22. 作为代码阅读者，我希望默认查看简要输入输出并能展开完整类型，以便兼顾扫描和准确核对。
23. 作为代码阅读者，我希望缺失解释明确显示未知，以便不被泛化文案误导。
24. 作为代码阅读者，我希望主线有明确触发、目标、输入和结果，以便理解一件完整的事。
25. 作为代码阅读者，我希望主线展示关键阶段及重要数据交接，以便同时理解业务过程和实现联系。
26. 作为代码阅读者，我希望关键规则、状态转换和失败路径可见，以便识别必须守住的行为约束。
27. 作为代码阅读者，我希望异步、重试、超时、事务与补偿边界可展开，以便不把同步返回误当整个过程完成。
28. 作为代码阅读者，我希望看到参与的函数、存储及外部系统，以便理解主线依赖。
29. 作为代码阅读者，我希望区分静态可能路径与指定 Execution 的 Runtime Observation，以便知道哪些行为确实被观测过。
30. 作为代码审阅者，我希望支付、权限、隐私和删除等敏感行为被标明，以便即使调用少也优先核查。
31. 作为代码审阅者，我希望公共函数的直接调用者及跨功能范围被标明，以便发现修改后果可能较广的位置。
32. 作为代码审阅者，我希望区分调用位置数、独立调用者数和其他引用，以便正确理解统计。
33. 作为代码审阅者，我希望影响分析显示有界路径和截断情况，以便不会把预算内结果误认为全部范围。
34. 作为代码审阅者，我希望 API、数据结构、配置、事件和公共协议的依赖缺口明确显示，以便不会把调用范围误认为完整爆炸半径。
35. 作为代码审阅者，我希望业务敏感标签附有依据和确认状态，以便判断其可靠性。
36. 作为代码审阅者，我希望操作可逆性与业务重要程度分开显示，以便理解出错后的恢复难度。
37. 作为代码审阅者，我希望常驻重要性与本次变更风险分开，以便不把注释修改和金额计算变化同等对待。
38. 作为代码审阅者，我希望看到明确比较版本中的行为前后差异，以便知道 AI 实际改变了什么。
39. 作为代码审阅者，我希望从行为变化下钻到主线、函数和源码差异，以便核对结论而非只接受摘要。
40. 作为代码审阅者，我希望区分已确认变化、静态关联和待核实影响，以便不过度推断修改后果。
41. 作为代码审阅者，我希望风险提示指出具体核查方向，以便决定下一步检查什么。
42. 作为代码审阅者，我希望验证结果关联到变化的行为或业务规则，以便知道测试通过究竟证明什么。
43. 作为代码审阅者，我希望本地逻辑测试和真实外部交互验收分开，以便不把模拟通过当成生产证明。
44. 作为代码阅读者，我希望所有解释显示所绑定的版本及失效状态，以便不依赖陈旧说明。
45. 作为项目维护者，我希望人工确认不被后续生成覆盖，以便保留业务知识的权威边界。
46. 作为代码阅读者，我希望从图中查看函数时保留原图，以便沿关系连续检查。
47. 作为代码阅读者，我希望进入函数后能回到来源主线、阶段或变更，以便不必重新定位。
48. 作为代码阅读者，我希望文件、函数及视图分别保存阅读位置，以便切换对象时保持上下文。
49. 作为代码阅读者，我希望各页面对齐、字号和文件类型标识一致，以便减少视觉跳跃。
50. 作为代码阅读者，我希望能按业务问题找到相关对象与 Evidence，以便不必预先知道函数名；无法回答时应说明缺口。
51. 作为项目维护者，我希望默认阅读离线且不运行被索引项目，以便理解代码不引入隐式外部操作。

## Implementation Decisions

- 复用现有阅读数据投影、图模型、主线来源绑定及桌面阅读呈现职责。新增能力映射、重要性摘要和版本比较能力时优先扩展这些边界，不预先引入新框架或重构事实内核。
- 保持 Ready Snapshot 和 Semantic Overlay 不可变。SourceFile 是源码载体，Definition 是 Snapshot 内的声明地址；Definition Key 不能直接充当跨版本逻辑身份或 Capability 身份。
- 业务层级属于能力组织视图，自动提出的归属保持 Capability Candidate；人工确认记录来源和版本。共享依赖与归属分别建模，允许待归类内容。
- 不增加独立业务流页、控制流页、数据流页和证据页。按对象承载视图，右侧提供可核对依据；所有首屏优先职责、关键行为和核查重点。
- 文件目录默认简洁，函数条目只展示名称和一句用途；完整输入输出、类型、示例及其他定义按需展开。职责分组无可靠依据时回退源码顺序。
- 函数视图分为说明、关键逻辑、调用关系。原始 CFG 是 Behavior Fact 的依据，不直接等同于面向人的逻辑说明。语义步骤可组合已有语句，但必须保留对应 Evidence、关键分支和副作用。
- Application Flow 由入口、决策、数据变化、副作用及结果组成，不等同于最长调用链。运行观测只证明指定执行范围，不补成完整路径集合。
- 所有生成文案仅进入 llm_inferred、未验证的 presentation；保留 Claim Basis 和 Assertion Status。缺失、陈旧或不闭合的 Evidence 不以通用解释填补，也不得提升 Relation Candidate 为确定 Relation。
- 风险展示区分业务重要程度、潜在影响范围、可逆性和依据状态。首屏仅保留少量具体原因，不采用没有校准依据的统一分数，也不默认满屏警告。
- 调用统计分别计算调用位置与不同调用者。间接遍历遵循 Query Budget，处理循环、重复路径和截断，保留 Completeness、Coverage 与 unknown；非调用依赖未覆盖时明确声明限制。
- 变更阅读绑定明确的基线与目标 Snapshot。跨版本对应无法可靠确定时保留新增、删除或对应未知，不通过相同名称猜测稳定身份。无版本比较证据时不得生成确定的行为变化结论。
- 本次变更风险结合契约、分支、金额、状态、权限、幂等、事务、写入等实际差异；长期重要性不自动等于每次修改风险相同。
- 验证摘要关联具体规则或行为，区分静态检查、本地测试和真实运行证据；测试数量及覆盖率不等于正确性。
- 保持桌面布局、文件类型图标、稳定左边界和各对象阅读书签。图中点击保留图，明确“阅读此函数”才进入正文，并可返回来源上下文。
- 本规格确定职责和行为契约，不预定数据库表或新增网络 API。持久化人工决定、跨版本映射等若需扩展领域契约，应在对应阶段补充版本化设计并遵守已有准入边界。
- 交付阶段 A：业务分层、页面职责、文件减法、函数关键逻辑与调用关系。阶段 B：重要性、已知影响范围、行为差异及验证缺口。阶段 C：有依据的关键数据流、状态／异步及非调用依赖深化、运行观测呈现和按问题阅读。后续阶段未完成时不得将整体规格标为完成。

## Testing Decisions

- 待用户确认的测试边界：以现有阅读数据投影与图模型的公开输入输出作为主要自动化入口，使用绑定 Snapshot、Semantic Overlay、Evidence 的固定夹具验证用户可见信息；辅以少量桌面端到端旅程验证组合行为。不为每种页面创建独立测试层。
- 好的测试验证结果、来源、完整性和交互，不锁定内部函数拆分、CSS 类名、节点坐标或生成文案的逐字内容。
- 复用已有阅读器先例：Manifest-only 文件不丢失、源码摘要失配不显示为快照证据、函数源码顺序、未解析调用保持分离、折叠分组不丢函数和调用、主线片段严格绑定函数范围及源码摘要。
- 投影和图模型验收：业务树归属与共享依赖分离；待归类对象可访问；简单函数紧凑；关键条件、返回、异常和写入不被压缩丢失；未知关系不变为确定边。
- 风险夹具至少包含：少调用但资金敏感、多调用但简单的公共函数、同一调用者多个调用位置、合法递归、循环依赖、动态目标未知、预算截断和缺少非调用依赖的情况。断言原因和范围而非单一分值。
- 版本比较验收：注释变化不冒充业务变化，实际契约变化显示前后差异，跨版本对应未知不猜测，旧解释失效，人工确认不被生成内容覆盖。新增持久化契约时沿用存储读回及版本边界的公共入口补充验证。
- 主线验收包含成功、关键失败和异步路径；没有 Runtime Observation 时不出现“实际执行”结论；运行证据必须绑定对应 Snapshot 和 Execution。
- 桌面旅程：能力概览进入主线与函数并返回；目录与全局搜索一步进入函数；图预览保持上下文；文件和函数对齐一致；书签按对象恢复；变更入口下钻后能返回同一比较；展开 Evidence 可核对原始依据。
- 回归 Gold 可证明一致性，但不作为独立语义正确性证据。增加人工编写的正反例；复用现有冻结真实语料检查集成，不运行任意被索引应用。
- 每阶段运行受影响定向测试和类型检查；只有跨层契约或发布范围变化才扩大必要门禁。此前原型测试通过不代表本规格的新功能已验收。
- 产品效果通过固定阅读任务评估：使用者能否说清职责、关键行为、变化与核查点，记录误解和依据定位成本；未测量前不宣称效率提升比例。

## Out of Scope

- 手机及平板专项适配；本次以桌面阅读为验收场景。
- 全仓库默认巨图、通用绘图编辑器、为每种分析类型新增独立页面。
- 自动修改、审批、合并、部署被索引代码，或将风险标签作为自动放行决定。
- 无 Evidence 的完整业务架构、完整爆炸半径或完备动态执行分析承诺。
- 未经授权调用外部模型、上传源码、运行被索引项目或接入真实支付等外部系统。
- 未经校准的统一风险评分、用测试数量代替行为正确性、用旧截图状态判断当前实现。
- 强制业务分类、跨版本名称匹配冒充稳定身份、覆盖人工确认或改写权威 Snapshot／Semantic Overlay。
- 阶段 C 不承诺一次支持所有语言、框架及外部协议；支持范围应显式声明，缺口保持可见。
