# 项目理解与需求核对闭环

## Problem Statement

当前阅读器已经能让读者选中文件或函数，阅读中文职责、输入输出和处理逻辑，并下钻源码。但读者尚不能顺畅回答：项目解决什么问题、应从哪里开始、一件事如何跨模块完成、某条需求由哪些条件保证，以及已有测试究竟证明了什么。

2026-09-08 的独立团队评估发现，冻结交付中的 179 个文件和 2260 个函数／方法已具备解释，但项目主线数据为空；普通搜索不检索中文说明，“索引”无法发现已有相关解释；能力候选仍主要是结构组织与词元建议。说明数量的完整不能代替整体理解和需求验收。

版本与哈希核验通过，但 8 个函数的定性抽查发现一处重试前置条件省略。因此流畅摘要不能直接成为完整行为契约。重型事实与 Evidence 全量内嵌、底层控制流节点过密，也增加了启动与阅读负担；目前没有冷启动基准或真实新读者对照实验。

本规格解决从项目认识、行为定位到逐条需求核对之间的断点，保留已有局部阅读能力与证据边界。

## Solution

读者打开项目后先看到项目目的、分析范围、核心能力与推荐阅读入口；可以按中文职责或业务问题检索相关实现，再沿有 Evidence 支持的 Application Flow 理解触发、关键条件、数据交接和结果。

读者可以把一组明确版本的需求条款整理为轻量核对表，每条连接规则、主线、Definition、Evidence 和验证产物，明确“支持、违反、缺少证据”，并区分静态判断、本地测试与真实运行观测。

先交付项目总览、中文检索、真实主线和需求核对的完整旅程，再改善解释精度、行为表达及数据加载。通过固定阅读任务衡量结果，不以解释覆盖率或图节点数量代表理解效果。

## User Stories

1. 作为首次接触项目的读者，我希望首页说明项目解决的问题，以便先建立阅读目标。
2. 作为首次接触项目的读者，我希望看到分析的版本、语言和源码范围，以便知道结论适用于哪里。
3. 作为首次接触项目的读者，我希望看到少量核心能力及简明职责，以便形成整体认识。
4. 作为首次接触项目的读者，我希望每项核心能力有推荐入口和推荐理由，以便知道先读什么。
5. 作为代码阅读者，我希望能力说明和入口带有来源与确认状态，以便区分候选、人工判断和静态依据。
6. 作为代码阅读者，我希望目录归属与业务能力分开，以便不把结构聚类当成业务架构。
7. 作为代码阅读者，我希望没有业务映射的源码仍可从目录找到，以便不丢失阅读范围。
8. 作为代码阅读者，我希望重复名称的候选显示路径和职责差异，以便辨别对象。
9. 作为项目维护者，我希望人工核对的能力和入口不被重新生成覆盖，以便保留已有判断。
10. 作为代码阅读者，我希望用中文文件职责和函数用途搜索，以便不必先知道英文标识符。
11. 作为代码阅读者，我希望使用经核对的业务别名定位对象，以便用自己的问题开始阅读。
12. 作为代码阅读者，我希望搜索结果说明命中的职责或行为，以便判断相关性。
13. 作为代码阅读者，我希望相关实现与已核对入口分别标明，以便不把关键词命中当入口证明。
14. 作为代码阅读者，我希望同名结果可以消歧，以便进入正确文件和 Definition。
15. 作为代码阅读者，我希望无法直接回答的问题仍能找到相关实现，以便继续调查。
16. 作为代码阅读者，我希望没有匹配、问题不受支持和分析不完整分别说明，以便选择下一步。
17. 作为代码阅读者，我希望搜索不裁剪源码目录，以便保留原有结构上下文。
18. 作为代码阅读者，我希望进入一条主线前知道触发、目标、输入和结果，以便判断它是否对应我的问题。
19. 作为代码阅读者，我希望主线按关键阶段组织，以便理解跨函数协作。
20. 作为代码阅读者，我希望看到阶段之间的数据和状态交接，以便理解行为的因果联系。
21. 作为代码阅读者，我希望看到影响结果的关键条件，以便识别实际业务规则。
22. 作为代码阅读者，我希望成功、失败、提前返回和恢复边界可见，以便不会只读到理想路径。
23. 作为代码阅读者，我希望异步、重试、事务和副作用的前提明确，以便不把可能发生误读为必定发生。
24. 作为代码阅读者，我希望每个主线阶段可以下钻对应源码与 Evidence，以便核对解释。
25. 作为代码阅读者，我希望下钻后能返回同一主线和阶段，以便连续阅读。
26. 作为代码阅读者，我希望没有主线时看到原因和可用替代入口，以便不面对无说明的空白区域。
27. 作为代码阅读者，我希望静态路径与指定执行的 Runtime Observation 分开，以便判断证据能证明什么。
28. 作为需求审阅者，我希望导入一组带身份与版本的需求条款，以便逐条核对而不是只看整体摘要。
29. 作为需求审阅者，我希望每条需求保留原始表述和来源，以便不被改写后的解释替代。
30. 作为需求审阅者，我希望把需求连接到主线、规则条件和 Definition，以便定位实现位置。
31. 作为需求审阅者，我希望每条判断附有具体 Evidence，以便独立复核支持或违反的理由。
32. 作为需求审阅者，我希望缺少证据时保持未知，以便不会把未发现问题当满足需求。
33. 作为需求审阅者，我希望记录相互冲突的依据，以便暴露尚未解决的判断分歧。
34. 作为需求审阅者，我希望测试结果说明覆盖哪条规则及什么场景，以便知道通过结果的证明范围。
35. 作为需求审阅者，我希望区分静态检查、本地测试与真实环境验证，以便避免验收层级混淆。
36. 作为需求审阅者，我希望源码或需求版本变化后旧判断显示待复核，以便避免沿用陈旧结论。
37. 作为需求审阅者，我希望保存并导出核对表及缺口，以便交接复核工作。
38. 作为代码阅读者，我希望文件职责区域持续显示 AI 推断的未验证状态，以便扫描目录时也知道来源。
39. 作为代码阅读者，我希望复杂函数摘要保留关键前提、异常和副作用，以便不因压缩误解行为。
40. 作为代码阅读者，我希望简单函数用紧凑步骤展示，以便不需要追踪庞大画布。
41. 作为代码阅读者，我希望逻辑图使用动作、条件和结果表达，并能展开底层依据，以便兼顾理解与检查。
42. 作为代码阅读者，我希望先看到总览和目录，再按需取得重型依据，以便尽早开始阅读。
43. 作为代码阅读者，我希望依据加载失败或版本不符时有明确提示和重试入口，以便不会看到错误版本的内容。
44. 作为项目维护者，我希望用固定的新读者任务检验交付，以便衡量是否真正缩短理解路径。
45. 作为项目维护者，我希望分别记录耗时、误解和依据定位成本，以便不把页面可操作当成理解成功。
46. 作为项目维护者，我希望默认阅读保持离线且不运行被索引应用，以便阅读操作不产生隐式外部影响。

## Implementation Decisions

- 本规格是现有分层阅读和变更审阅规格的增量验收闭环。复用阅读数据投影、能力导航、Application Flow、统一搜索、源码／Evidence 面板、比较与验证记录边界；不重建阅读器或事实内核。
- 项目总览采用目的、分析范围、核心能力、推荐入口和阅读顺序的紧凑结构。先呈现任务内容，来源细节按需展开，但候选与未验证状态持续可见。
- Capability 与目录结构保持不同含义。自动内容仍为 Capability Candidate；人工确认记录操作者、理由和所绑定版本。缺少充分依据时展示候选或缺口，不通过命名修饰制造确定性。
- 检索扩展为确定性的本地索引，覆盖文件职责、函数用途、已有主线标题和经核对别名，保留标识符和路径检索。无需引入在线模型或向量服务。
- 搜索结果携带对象身份、命中说明、来源和 Snapshot；精确名称及核对别名优先于一般说明文本。相关性排序不提升 Claim Basis，也不将搜索命中自动认定为入口。
- 保留已有受控 Query Intent 和消歧能力。不支持的问句可回退相关对象检索，但明确没有回答原问题；不得生成没有 Evidence 的解释性答案。
- 首批以现有冻结 CodeGraph 语料交付索引、增量同步、上下文去重三条代表性 Application Flow。以独立源码核对建立阶段与关键边界，保留无法闭合部分；不把最长调用链或一次运行轨迹当作完整主线。语料专用描述进入版本绑定数据，不硬编码进通用呈现逻辑。
- Application Flow 包含触发、输入、目标、阶段、关键条件、数据与副作用、结果和未知项。每个可核对的阶段引用有效 Definition 与 Evidence；缺少必要依据时标记不可用或部分可用，并给出目录／函数替代入口。
- 新增轻量、可导入导出的需求核对投影，复用现有本地版本化记录模式。需求条款具有独立的集合身份、条款身份、版本、原文和来源；不能使用 Definition Key 代替需求身份。
- 一条核对记录绑定需求版本、Repository、目标 Snapshot、适用的 Semantic Overlay，以及主线／Definition／Evidence 引用、规则条件、判断、理由和验证产物。非适用字段可缺省并说明原因，不能借缺省绕过版本校验。
- 判断采用支持、违反、缺少证据；支持或违反需要有效依据和可审查理由。判断同时展示证明层级；静态支持不等于真实运行验收通过。存在未解决的相反证据时保留冲突与待复核状态，不输出无条件通过。
- 验证产物说明所覆盖的条款、条件或行为，并沿用静态检查、本地测试、运行观测的区分。没有运行证据时明确未验证真实执行；不因测试数量增加自动提升判断。
- 需求版本或源码 Snapshot 变化后旧记录保留历史但不沿用为当前结论。跨版本对应必须显式建立，不以同名猜测；导入和读回均校验身份与引用，人工决定不被生成覆盖。
- Snapshot 与 Semantic Overlay 保持不可变；新增总览、解释、主线呈现和核对记录不能改写权威事实。AI 文案仅为 `llm_inferred`、未验证 presentation，人工复核记录与模型原始来源分开保存。
- 修正已发现的重试条件省略，以复杂异步、异常和副作用函数建立风险抽查集。摘要至少保留决定行为是否发生的前提，不要求逐句翻译全部源码。
- 函数关键逻辑优先呈现动作、条件、结果；可折叠直线步骤，但保留关键分支、异常、提前返回和 Evidence。简单函数可用文字步骤，复杂函数保留可展开图及原始依据。
- 阅读包拆分轻量总览／目录／解释与按需加载的源码、Fact、Evidence 分片，由版本化清单和内容摘要绑定。保留离线本地阅读入口；缺失、错绑或加载失败不能回退为另一版本的数据。具体打包形式在实现时沿用现有预览入口，不预建新后端。
- 性能工作限定于阅读包加载和呈现。先在冻结语料及固定环境记录冷启动、可交互时间、载荷和内存，再比较改动；不借此改写语法抽取性能 ADR，不预建 worker pool、native runtime 或全仓缓存架构。
- 实施顺序为总览／检索／真实主线，随后需求核对与证据验证，最后行为表达和加载改进。每一阶段独立验证；未完成全部范围时不把整体目标标记完成。

## Testing Decisions

- 已确认测试边界：以现有“冻结阅读数据输入 → 阅读器用户旅程”的组合入口为主，复用查询、主线、比较验证记录的公开输入输出补充错误路径；不为每个页面新增独立测试层。用户已在确认拆票时一并认可此边界。
- 好的测试验证读者能找到什么、结论依据是什么、缺口是否可见及返回上下文是否连续，不断言内部函数划分、CSS 类名、画布坐标或生成文案逐字一致。
- 复用现有测试先例：Manifest-only 文件保留、源码摘要失配拒绝、主线引用严格绑定函数范围、同名查询消歧、未知调用分离、人工决定读回与失效、验证记录绑定比较版本并区分本地测试和实际执行。
- 自动化组合旅程覆盖：项目总览 → 中文问题 → 相关能力／主线 → 阶段 → 函数 → Evidence → 返回；需求条款 → 规则条件 → 依据与验证 → 保存／读回／导出。不得仅以静态 HTML 包含文字视为旅程通过。
- 查询正反例覆盖中文职责命中、已有精确问句兼容、别名、同名消歧、无匹配、不支持问句的诚实回退、失效解释排除、候选不冒充确认入口。冻结 10 个不含函数名的问题，由独立源码复核确定相关对象；至少 8 个问题的前 5 项结果包含有效相关入口或实现。
- 三条真实主线各覆盖触发到结果、关键条件以及实际存在的失败／异步边界；每个阶段可回到正确源码。人工独立核对关键规则，不能仅用同一生成器的输出作预期答案。缺少运行观测时不得出现已执行结论。
- 需求核对使用 5 条从冻结上下文去重实现独立整理、版本明确的规则，另用受控夹具构造违反、缺证据和冲突场景；每条均能定位条件与 Evidence。只有源码依据的条款必须显示真实执行未验证。
- 记录导入／读回覆盖错误 Repository、Snapshot、需求版本、缺失 Evidence、篡改摘要、同名不同 Definition、旧验证产物和冲突判断；不满足绑定的记录不可成为当前支持结论。
- 将“未降级但没有待处理文件”“仍有待处理文件但已停止”“满足重试条件”作为关键前提正反例，核查解释与源码条件是否一致；本规格不要求执行被索引应用。
- 图压缩验收验证关键决策、提前返回、异常及副作用没有丢失；简单函数不强制画布。文件页与函数页均可直接识别解释未验证状态。
- 按需加载验收覆盖首屏无需解析全部 Evidence、展开时正确加载、缺失分片提示、重试、版本／摘要错配拒绝及完整性不变。固定环境至少记录 5 次独立冷启动的中位数与范围，区分单次观测和峰值；没有证据前不承诺具体提升比例。
- 真人效果验收邀请未参与实现且不熟悉该语料的读者完成任务：5 分钟内说明目的、三项能力及入口；10 分钟内解释增量同步的至少五个关键阶段和一个失败或未知边界；逐条核对五条规则。任务给出可点击依据，记录耗时、误解和证据定位成本。
- 与直接阅读源码的对照应使用同一任务难度并控制先后学习影响；初次小样本只提供定性结果和原始记录，不宣称统计显著的普遍效率提升。以上时间和检索比例是本规格验收目标，不是已取得成绩。
- 仅规格阶段做模板、术语、引用和范围检查，不把既有测试收据当作本规格通过。实现时先运行受影响定向测试和类型检查，跨层数据契约与发布再扩大必要门禁。

## Out of Scope

- 大型需求管理系统、多人审批流程、外部工单同步或自动业务验收放行。
- 任意自然语言问题的完备问答、未经授权的在线模型／向量服务、源码外传或执行任意被索引项目。
- 自动推导全部业务能力、完整动态路径、全部影响范围，或用结构覆盖率冒充业务理解率。
- 改写权威 Snapshot／Semantic Overlay、将模型文案升级为事实、通过名称猜测跨版本身份。
- 重新实现已有双快照比较、风险分析及验证导入能力；既有任务仍按自身范围验收。
- 修改被索引 CodeGraph 的业务实现。本规格修正的是阅读器说明和组织方式。
- 手机／平板专项适配、全仓库默认巨图、通用图编辑器、语法内核或 runtime 架构重写。
- 修改既有 Issue 状态、提交工作区修改或部署产品。

## Further Notes
